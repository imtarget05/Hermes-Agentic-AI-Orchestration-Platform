## Known Security Issues (fix before showcasing)

Four items were requested here: **three confirmed, one disproved.** I report only what I personally reproduced.

**1. API auth fails open when no token is configured - `src/hermes/api.py:36`, `src/hermes/api.py:101-103`. `VERIFIED`**
`API_TOKEN = os.environ.get("HERMES_API_TOKEN", "")` and `_check_auth` is `if API_TOKEN and x_api_token != API_TOKEN: raise HTTPException(401)`. With the default empty value the `and` short-circuits and **no endpoint requires any credential**. I ran it: `API_TOKEN default: ''` -> `GET /tasks` with no token -> **200**. When a token *is* set the gate works correctly (`no header -> 401`, `wrong token -> 401`, `right token -> 200`). Fix: fail closed, or refuse to start without a token outside dev mode.

**2. Telegram webhook registration/deletion is unauthenticated - `src/hermes/telegram_chat/webhook.py:100-113` and `:116-123`. `VERIFIED`**
`POST /telegram/webhook/set` and `DELETE /telegram/webhook` call neither `_check_secret` nor any token check, unlike `POST /telegram/webhook`, which does call `_check_secret` at `:49`. (Path note: the brief said `/api/telegram/webhook/set`; the router is mounted with no prefix - `api.py:27`, `webhook.py:6` - so the real path is `/telegram/webhook/set`.) With a bot token set, **any unauthenticated caller can redirect the bot's webhook to an attacker-controlled URL**, i.e. hijack all chat traffic. Compounding this, `_check_secret` itself fails open: `if expected and secret_header != expected` (`webhook.py:33`) - I confirmed an empty secret (the default, `config/__init__.py:26`) accepts any request, and only a configured secret produces a 403.

**3. Identity is client-asserted - `src/hermes/api.py:81-83` and `src/hermes/telegram_chat/auth.py:62-73`. `VERIFIED`**
`_get_user_from_request` resolves the caller from a plain request header: `user_header = request.headers.get("X-User-ID")` -> `engine.get_user(user_header)`. Nothing binds that header to a verified principal, so anyone can claim any identity - including the seeded `admin` user `user_4` (`telegram_chat/auth.py:30`). I ran it: with `API_TOKEN` empty, a request carrying only `X-User-ID: user_4` and no credential returned **200 and enumerated all 4 users** via `GET /auth/users`. The Telegram path has the same shape - `get_user_from_telegram(user_id, username)` (`auth.py:62-73`) trusts `user_id`/`username` from the update body, which is only trustworthy if the webhook secret is set (see item 2). Fix: derive identity from a signed token, not a self-declared header.

**4. The learning loop computes insights nothing consumes, and `auto_resolution_rate` can only be 0 or 1 - `src/hermes/loops.py`. `NOT VERIFIED - the claim is false as stated.`**
`src/hermes/loops.py` **does not exist**, and the string `auto_resolution_rate` appears **nowhere** in `src/` or `tests/`. The real learning loop is `LearningLoop` at `src/hermes/async_engine/loops/audit.py:17`, and both halves of the claim are wrong. (a) Its output **is** consumed: `refresh_policy()` (`:65-69`) persists mined retry budgets to `hermes_policy.json`, `load_policy()` (`:72-76`) reads it, `loops/pipeline.py:37-63` calls both and returns the result as `{"8_learning": {"policy": policy}}`, and `loops/planner.py:21-26` carries the corresponding `DEFAULT_MAX_ATTEMPTS` budget table. (b) There is no 0-or-1 metric to critique - `failure_patterns` (`:25-46`) computes a genuine continuous `failure_rate` (`round(failed/total, 3)`) and `policy_suggestions` (`:49-63`) branches on the thresholds `>= 0.5` and `<= 0.05`. **There is nothing to fix here; I am not reporting a non-issue.** The one legitimate criticism nearby is that `LearningLoop` reaches into the private `store._exec` (`:27,36`) rather than a store method, coupling it to SQL details.
